Ericsson's [ecChronos](https://github.com/Ericsson/ecchronos) schedules repairs for Apache Cassandra, and its `core.impl` module has the kind of README most teams only intend to write. It goes through the module class by class and says what each one does. Of `NodeWorker`, the background thread that runs for each Cassandra node, line 136 says:

> Calls `RepairScheduler.putConfigurations()` to keep jobs up to date

Pull request [#1786](https://github.com/Ericsson/ecchronos/pull/1786), *"Add Repair History pre and post Job in Incremental path"*, changed 27 files (+1,235 −417). Part of it was a tidy refactor: a new class, `SchemaRefresher`, took over turning schema events into repair configurations. `NodeWorker` lost 150 lines, now holds a `SchemaRefresher`, and hands every event to it. It no longer references `RepairScheduler` at all. The call the README describes is still made, from line 158 of `SchemaRefresher.java`.

The pull request was approved and merged on 8 September. The README was not in the diff, so nobody reading the diff had a reason to open it. At the time of writing, line 136 on `master` still credits `NodeWorker`, and so does the execution-flow sketch at line 156 of the same file.

That used to cost one confused engineer some time. It now costs more, because a design doc has a second reader. Coding agents read `AGENTS.md`, `CLAUDE.md`, READMEs and architecture notes as context before they write anything, so a decision written down once steers thousands of generated lines, and a constraint nobody wrote down does not exist for the agent writing your code. The same sentence also goes stale faster, because at agent volume the code changes constantly and nothing in the merge path compares it with the prose. The diff shows the code. The sentence is in a different file.

Striff checked 28 rules from ecChronos's documentation at both revisions of the pull request. Three of them:

## A one-line fix, while it is still one line

The fix is one word in a README: `NodeWorker` becomes `SchemaRefresher`. In the pull request that caused it, that is a one-line follow-up commit, made while the author still remembers why the call moved. Left alone, the sentence costs someone time.

The next contributor looking for where repair configurations are scheduled is sent to `NodeWorker` by the README, spends a while reading a class that no longer does that, and finds `SchemaRefresher` only by giving up on the doc and reading the diff history. A coding agent handed the same README does something worse. It has an obvious way to make the sentence true again: give `NodeWorker` a scheduler and re-create the dependency the refactor had just removed. That is the path of least resistance for an agent that takes the doc at its word, and undoing it costs another round of review, more tokens, and another pull request to notice the regression a second time. A stale sentence like this one is a set of instructions for undoing your last refactor, and everyone who follows it before someone fixes it pays in wasted work.

## More than one class calling another

`NodeWorker` calling `RepairScheduler` is the simplest thing a document can say: one class, one reference. Documents also make claims about whole modules, about a word that stands for several packages at once, and about every class of a kind. The rule language has the quantifiers for those, and the same program answers them. Three more rules Striff read out of public repositories' own documents:

Apache Pinot's design note for its SQL DDL module says the module "depends only on" three things. Two of them are modules of the same repository and the third, `calcite-babel`, is an external library, so the rule is about which of Pinot's own modules it may use. Since the materialized-view work, the module's build has also pulled in `pinot-query-planner`, and `MaterializedViewSchemaInferer` imports from it. The sentence has been wrong ever since, and it still is. Striff reports it as already broken and never blames it on the pull request in front of it.

SubtitleEdit's command-line reference says the `seconv` tool uses "no Avalonia / GUI runtime". There is no namespace called GUI. The rule works because the word is bound to the two namespaces that are the GUI, and it held: `seconv` references neither. MonoGame-Extended's coding guidelines ask for static helper classes; six of its seven are, and `PrimitivesHelper` is not.

Every rule Striff reports gets one of four outcomes. It held, meaning nothing in this pull request breaks it. It was violated, meaning this change broke it. It was already broken in the code Striff checked, before this change, and that is never blamed on the change. Or it was restored: broken before, true after. Striff reports only what it can verify from the code, so a rule it cannot answer from a source parse is left out rather than shown as passing.

A check that fired on every pull request would be muted within a week, so a low rate is what we want. The 53 already-broken rows are the other quiet result: rules a repository's own documentation states that were already false in the code Striff checked, before the pull request. They are never blamed on the pull request in front of you, and they are never shown as a pass either. Whether the fix belongs in the code or in the sentence is the maintainer's call, and now the maintainer knows there is one to make.

## Writing docs that can be checked

You do not have to change how you write to get value from this. ecChronos's README was written for people, not for us. Sentences of a certain shape get checked, though, and it is worth knowing which.

Name real things. `NodeWorker` is checkable, and "the worker" is checkable only if one class answers to it. Backticks help a reader and cost nothing.

Say where things live and what they use. "`ConnectionType` is in `utils`" and "`NodeWorker` calls `RepairScheduler`" are placement and dependency claims, which are the relations a parser can answer at both revisions.

Say what must not happen. "The core never imports from plugins" is a rule the moment it is written down, and it is the kind of rule an agent in a hurry is most likely to break.

Leave intent as prose. "We prefer composition" is not a claim about structure, and nothing will pretend it is one.

Keep the agent files honest too. `AGENTS.md` and `.github/copilot-instructions.md` are read by the same process, so the layering and naming rules you give your agents are checked against the code they write.

## Where to start

If your team is leaning into AI-assisted development, write the decisions down, because agents will read them. Then have something check every pull request against them, because agents and humans will also break them, cleanly and plausibly, a few lines at a time, in files nobody thought to open.

[Install the GitHub App](https://github.com/apps/striff-app/installations/new) and open your next pull request. Striff reads the docs you already have and checks every rule in them, with nothing to write and nothing to configure.
