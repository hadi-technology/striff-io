Every coding agent starts the same way. Before it writes a line, it reads the repository's instruction file: `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`. Whatever that file says about the code, the agent takes as fact and builds on. It does not verify; it has no way to. And nothing else does either. Your tests check the code. Your types check the code. Nobody checks the document that the code is now generated from.

Here is what that looks like in the [official C# SDK for the Model Context Protocol](https://github.com/modelcontextprotocol/csharp-sdk), the protocol built to give AI models accurate context. Line 258 of its Copilot instructions:

`McpServerFactory` does not exist. It was deleted last December. Search the repository for the name and you get one result: this line, in the file every agent reads first.

<div class="bp-callout">
Copilot wrote that instruction. Seven weeks later, Copilot deleted the class it names. Ten months on, every agent that opens the repository is still told to use it.
</div>

The person who wrote a design doc in 2015 knew a colleague might read it, get confused, and ask. The agent reading line 258 today does not ask. It writes `McpServerFactory`, watches the build fail, and goes looking for what it should have done. That one is cheap: a few wasted turns. The reason to care is what it tells you about every other sentence in that file, and in yours.

## How the input to your codebase went wrong

None of the people involved would have caught this, because nothing they did required them to:

The reviewer of the instructions read a long document and it was almost entirely right. The reviewer of the removal read a diff and the document was not in it. That is the whole mechanism. A document and the code it describes live in different files, and a pull request only ever shows you one of them.

## The agent doesn't just read the wrong sentence. It repeats it.

In April 2026 a commit authored as "Architecture Bot" [added an Architecture section](https://github.com/yegor256/cactoos/commit/18a0c8ad8d8b64d6bbb62fa36e668f967afda2ac) to the README of [`yegor256/cactoos`](https://github.com/yegor256/cactoos). The commit message links a Claude Code session. The new section says:

> Explicit caching requires opting in with `Sticky` or `StickyList`.

`StickyList` was [removed in 2020](https://github.com/yegor256/cactoos/commit/eed03c1fc05217eeda0564999cae2c87709b1e13). It survived in a comparison table further up the same README, an agent asked to describe the architecture read that table, and the old name came out the other side as a confident new instruction with a fresh timestamp. The next agent to open that README now has two sentences telling it to use a class that isn't there, and the newer one looks authoritative.

<div class="bp-callout bp-callout--amber">
A wrong sentence in a doc used to cost one confused engineer an afternoon. Now it is read by every agent run, acted on without question, and copied into the next document.
</div>

## The sentences that don't fail the build

A stale class name is the version of this problem you can see. The agent trips over it and recovers. The expensive version is silent.

<p class="bp-figure-title">Two ways an agent strays from the docs</p>
<div class="bp-outcomes">
<div class="bp-outcome bp-outcome--amber"><p class="bp-outcome-name">It follows a sentence that is no longer true</p><p class="bp-outcome-desc"><em>&ldquo;Use <code>McpServerFactory</code>.&rdquo;</em> The build breaks, the agent recovers, you pay in turns and tokens. If the sentence describes a pattern rather than a class, the build doesn&rsquo;t break, and the agent reproduces a design the team retired.</p></div>
<div class="bp-outcome bp-outcome--danger"><p class="bp-outcome-name">It ignores a sentence that is still true</p><p class="bp-outcome-desc"><em>&ldquo;Controllers go through the service layer.&rdquo; &ldquo;<code>core</code> never imports from <code>plugins</code>.&rdquo;</em> The agent takes a shortcut. The code compiles, the tests pass, the diff looks fine, and the document that forbade it is not in the diff. Merged.</p></div>
</div>
</div>

The second one is where architecture goes. Not in one dramatic change but in a hundred small ones, each of which compiled, each reviewed as a diff, each contradicting a sentence nobody had open. A year later the layering the team agreed on is a description of a system that no longer exists, and every change costs more than it should.

We build [Striff](https://striff.io) to close that gap. It reads the documents already in a repository, turns each sentence that makes a claim about the code into a rule, and checks the rule against the parsed code before and after every pull request. We ran it over roughly six hundred recent public pull requests in Java, C#, TypeScript and Python. From those repositories' own documentation it read 7,161 rules:

Spring AI's is the one to think about. Its speech documentation still builds a whole walkthrough on `OpenAiAudioApi`, five months after the project moved to the official OpenAI Java SDK. An agent asked to add text-to-speech reads twenty sentences describing a design the maintainers deliberately replaced. It will either fail the build and recover, or, if it is resourceful, rebuild the old design on top of the new one.

## Why nothing you already run catches this

Every check in a pipeline compares code to code. Tests execute it, types constrain it, the linter parses it, the dependency audit reads a manifest. A sentence in a markdown file is in none of those places. It is not compiled, not executed, and not in the diff, so no reviewer has a reason to open it and no tool has an opinion about it.

<div class="bp-callout">
The sentence and the code that contradicts it are both plainly visible. They are just never visible to the same reader at the same moment.
</div>

None of this is hard to check. "`core` must not import from `plugins`" is a one-line question about a dependency graph, and your compiler answers harder questions on every build. What was missing is anything that turns the sentence into the question.

## What to do about it

- **Treat your agent instruction files as code.** They are an input to your codebase now. When you delete or rename a type, `git grep -w OldName -- '*.md'` takes a second, and IDE rename refactorings skip markdown.
- **Keep them short, and prefer rules to names.** "Controllers never call repositories directly" stays true across a hundred refactors. A class name is a claim that can go stale on the next one.
- **Have the docs checked on the pull request**, where the change that contradicts them is being reviewed. This is what the MCP finding looks like when Striff posts it:

<div class="bp-note">
<p class="bp-note-title">Method notes</p>
<p>Roughly six hundred recent public pull requests across several hundred repositories in Java, C#, TypeScript and Python. Code is parsed from source without compiling it, so the model has no generated members and no resolved annotations; where that leaves a rule unanswerable, the check reports nothing rather than a pass or a failure. A documented type counts as absent only on an exact-token match against the whole revision, with the repository&rsquo;s history checked to tell a moved type from a removed one.
