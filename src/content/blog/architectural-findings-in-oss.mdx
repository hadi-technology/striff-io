Before a coding agent touches a repository, it reads an instruction file: `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`. The agent treats whatever that file says as true about the code. Nothing checks it against the code.

Here is line 258 of the one in the [official C# SDK for the Model Context Protocol](https://github.com/modelcontextprotocol/csharp-sdk), the protocol that exists to give AI models accurate context:

`McpServerFactory` was deleted on 2 December 2025. Search the repository for the name today and line 258 is the only result. The only place the class still exists is the file agents read first.

One stale line is a small thing. Where it sits is what makes it worth a post. It is in the one file whose only job is to be right for agents, in the SDK of the protocol built to give models context, and every commit around it was reviewed and merged by experienced maintainers. If it happens there, it is happening in repositories with far less attention on them. And agents don't only read these files. As the second example below shows, they write new documentation from them.

We build [Striff](https://striff.io), which checks pull requests against what a repository's own documentation says about its code. This post is about lines like 258: how one gets written, what we found when we looked for more in public repositories, and what makes them harder to find than they look.

Nobody in that history did anything careless. Copilot described a class that existed and compiled. The attribute announcing its removal was in a different file from the one being written. The reviewer read a long document that was almost entirely accurate. The removal PR did exactly what its title said, and the instructions file was not part of it, so nobody reviewing it had a reason to open that file. The four later edits each had a job to do, and none of them needed line 258.

Every step was reasonable, and the result is a sentence that has been telling agents to use an API that does not exist for ten months. No file in the repository links a sentence in a markdown file to the symbol it names, so nothing could have failed when the symbol went away.

This particular failure is cheap. An agent that follows line 258 writes code that does not compile, reads the error, and goes looking for the replacement. That costs turns and tokens, not correctness. The expensive cases are the ones that compile, and we come back to those below.

## Stale docs get copied into new docs

In April 2026 a commit authored as "Architecture Bot" [added an Architecture section](https://github.com/yegor256/cactoos/commit/18a0c8ad8d8b64d6bbb62fa36e668f967afda2ac) to the README of [`yegor256/cactoos`](https://github.com/yegor256/cactoos). The commit message links a Claude Code session, and the pull request was opened and merged by people. The new section says:

> Explicit caching requires opting in with `Sticky` or `StickyList`.

`StickyList` was [renamed in December 2018](https://github.com/yegor256/cactoos/commit/be02845a55f191007cd60770a455b59d7320446d), and the list decorator it became was [removed in February 2020](https://github.com/yegor256/cactoos/commit/eed03c1fc05217eeda0564999cae2c87709b1e13). But 53 lines above the new section, the README's comparison table has listed `StickyList` since 2017.

We can't see the session, but the likely sequence is plain: an agent asked to describe the architecture read the README, and the README said `StickyList`. Agents don't only read stale sentences. They also write new documents from them, and those documents look fresh.

## Looking for more

We ran Striff over 609 recent pull requests in 542 public Java, C#, TypeScript and Python repositories. One of the things it looks for is a type name that a repository's documentation mentions and its code does not declare, and it checks the repository's history to tell a type that moved from one that is gone.

These are the cases we checked by hand and could confirm. Each name is in the project's current documentation and absent from its current code on an exact-token search, and each was deleted in the commit linked.

## Why a grep isn't enough

The obvious first attempt is a script. This one prints every `CapitalisedName` in backticks in a repository's docs that no non-doc file mentions:

```bash
git ls-files '*.md' '*.mdx' '*.adoc' \
  | xargs grep -ohE '`([A-Za-z0-9_]+\.)*[A-Z][A-Za-z0-9]+`' \
  | tr -d '`' | sed 's/.*\.//' | sort -u \
  | while read -r name; do
      git grep -qw -- "$name" -- ':!*.md' ':!*.mdx' ':!*.adoc' || echo "$name"
    done
```

On the MCP SDK it prints 19 names, including `McpServerFactory`. On cactoos it prints exactly one, `StickyList`. It is worth running on your own repository. But on Redis's Java client it prints 61, and on Redisson 156, and many of those are not mistakes:

A documentation page has plenty of good reasons to mention a type the code doesn't have: a migration guide or changelog describing a removal, a commercial edition, sample output, an external library, a type that moved to another module. Whether a mention is a claim about this codebase depends on the sentence around it. Detecting the absence is easy. Deciding whether the document is wrong means reading the sentence, and checking the repository's history to see whether the name was ever there and where it went. Every row in the first table passed both.

## The rules that compile

A stale class name fails loudly the first time anyone uses it. The expensive sentences are architectural: *controllers go through the service layer*, *this module must not depend on that one*. An agent that follows an outdated one, or breaks a current one, produces code that compiles, passes its tests, and gets reviewed as a diff. The review doesn't include the document that stated the rule.

Striff's other check is aimed at those sentences. A language model reads each sentence in a repository's documentation and proposes the rule it states, as a formula over types and their references. A program then evaluates the formula against the parsed code before and after the pull request, so the model proposes rules but never decides verdicts. Across the 609 pull requests it extracted 7,161 rules from the repositories' own documentation. [How a sentence becomes a check](/blog/design-docs-are-enforceable-now) walks through one end to end.

## What other people have measured

Treude and Baltes [looked at agent configuration files in 356 repositories](https://arxiv.org/html/2606.09090v1) and found 230 stale references to code elements in 82 of them (23% of repositories, though only about 1.3% of the references they checked). How much a stale instruction degrades an agent's output is, in their words, an open question: "When stale, such descriptions can degrade AI assistance without any visible error."

There is also a case for writing less. Gloaguen et al. [evaluated AGENTS.md-style files](https://arxiv.org/abs/2602.11988) and found they do not generally improve task success while raising inference cost by over 20%. Every name in one of these files is a claim that can go stale, so a short file is also cheaper to keep true.

## What to do about it

- **Search the docs when you delete or rename a type.** `git grep -w OldName -- '*.md'` takes a second, and IDE rename refactorings often skip markdown.
- **Keep agent instruction files short**, and prefer describing structure to naming classes.
- **Run the script above** occasionally, and read its output rather than failing a build on it.

Striff runs both checks on every pull request as a [GitHub App](https://striff.io): the names a change leaves stranded in your docs, and the architectural rules your docs state. It uses the documents already in the repository, so there's no rule file to maintain.
