Before a coding agent touches a repository, it reads an instruction file: `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`. Everything in that file is taken as true about the code. Nothing checks it against the code.

Here is line 258 of the one in the [official C# SDK for the Model Context Protocol](https://github.com/modelcontextprotocol/csharp-sdk). MCP is the protocol whose entire purpose is giving AI models accurate context:

`McpServerFactory` was deleted on 2 December 2025. Search the repository for the name today:

<span class="bp-keystat-value">1</span>
<span class="bp-keystat-body">result for <code>McpServerFactory</code> in the whole repository. It is line 258, in the file every agent reads first. The class it names has been gone for <b>ten months</b>.
<span class="bp-keystat-src">modelcontextprotocol/csharp-sdk &middot; 4.5k stars &middot; checked 24 Sep 2026</span></span>

One stale line is a small thing. Where it sits is what makes it a post. This is the one file whose only job is to be right for agents, in the SDK of the protocol built to give models context, and every commit around it was reviewed and merged by experienced maintainers. If it happens there, it is happening in repositories with far less attention on them. And, as the second example below shows, agents don't only read these files. They write new documentation from them.

We build [Striff](https://striff.io), which checks every pull request against what a repository's own documentation says about its code. This post is about lines like 258: how one gets written, how many we found in public repositories, how long they have been wrong, and why finding the ones that matter takes more than a grep.

## How line 258 happened

Nobody in this history was careless. Follow the dates:

Copilot described a class that existed and compiled. The attribute announcing its removal was in a different file from the one being written. The reviewer read a long document that was almost entirely accurate. The removal PR did exactly what its title said, and the instructions file was not part of it, so nobody had a reason to open it. The four later edits each had a job to do, and none of them needed line 258.

<div class="bp-callout">
Every step was reasonable. The result is a sentence that has been sending agents to an API that does not exist for ten months, because nothing in a repository links a sentence in a markdown file to the symbol it names.
</div>

This particular failure is cheap. An agent that follows line 258 writes code that does not compile, reads the error, and goes looking for the replacement. That costs turns and tokens, not correctness. The expensive cases are the ones that compile, and we come back to those below.

## Stale docs get copied into new docs

In April 2026 a commit authored as "Architecture Bot" [added an Architecture section](https://github.com/yegor256/cactoos/commit/18a0c8ad8d8b64d6bbb62fa36e668f967afda2ac) to the README of [`yegor256/cactoos`](https://github.com/yegor256/cactoos). The commit message links a Claude Code session; the pull request was opened and merged by people. The new section says:

> Explicit caching requires opting in with `Sticky` or `StickyList`.

`StickyList` was [renamed in December 2018](https://github.com/yegor256/cactoos/commit/be02845a55f191007cd60770a455b59d7320446d), and the list decorator it became was [removed in February 2020](https://github.com/yegor256/cactoos/commit/eed03c1fc05217eeda0564999cae2c87709b1e13). But 53 lines above the new section, the README's comparison table has listed `StickyList` since 2017.

The likely sequence is plain: an agent asked to describe the architecture read the README, and the README said `StickyList`. So a six-year-old mistake got a fresh timestamp, a confident imperative sentence, and a place in the file everyone reads first.

<div class="bp-callout bp-callout--amber">
Agents don't only read stale sentences. They write new documents from them, and the new documents look fresh.
</div>

## How long these lines have been wrong

We ran Striff over 609 recent pull requests in 542 public Java, C#, TypeScript and Python repositories. One of the things it looks for is a type name that a repository's documentation mentions and its code does not declare, checking the repository's history to tell a type that moved from one that is gone.

## Why a grep isn't enough

The obvious first attempt is a script. This one prints every `CapitalisedName` in backticks in a repository's docs that no non-doc file mentions:

```bash
git ls-files '*.md' '*.mdx' '*.adoc' \
  | xargs grep -ohE '`([A-Za-z0-9_]+\.)*[A-Z][A-Za-z0-9]+`' \
  | tr -d '`' | sed 's/.*\.//' | sort -u \
  | while read -r name; do
      git grep -qw -- "$name" -- ':!*.md' ':!*.mdx' ':!*.adoc' || echo "$name"
    done
```

On the MCP SDK it prints 19 names, including `McpServerFactory`. On cactoos it prints exactly one, `StickyList`. It is worth running on your own repository. But on Redis's Java client it prints 61, and on Redisson 156, and many of those are not mistakes:

<p class="bp-figure-title">Missing from the code, and the docs are right</p>

<div class="bp-audit-row"><span class="bp-audit-repo">redisson/redisson</span><span class="bp-audit-saw"><code>RClusteredMap</code> and five more are not in the code</span><span class="bp-audit-true">They belong to Redisson PRO, the closed-source edition, and the docs say so.</span></div>

A documentation page has plenty of good reasons to mention a type the code doesn't have: a migration guide describing a removal, a commercial edition, sample output, an external library, a type that moved to another module. Whether a mention is a claim about *this* codebase depends on the sentence around it and on the repository's history: was the name ever declared here, and where did it go? Detecting the absence is the easy half. Every row in the first table passed the hard half.

A stale class name fails loudly the first time anyone uses it. The sentences to worry about are the ones that don't:

Striff's second check is aimed at those sentences. A language model reads each sentence in a repository's documentation and proposes the rule it states, as a formula over types and their references. A program then evaluates the formula against the parsed code before and after the pull request. The model proposes rules; it never decides verdicts. Across the 609 pull requests it extracted 7,161 rules from the repositories' own documentation:

Treude and Baltes leave the important question open. How much a stale instruction degrades an agent's output is, in their words, unknown: "When stale, such descriptions can degrade AI assistance without any visible error." Gloaguen's result cuts the other way and points at the same fix: every name in an agent file is a claim that can go stale, so a shorter file is cheaper to run and cheaper to keep true.

## What to do about it

- **Search the docs when you delete or rename a type.** `git grep -w OldName -- '*.md'` takes a second, and IDE rename refactorings often skip markdown.
- **Keep agent instruction files short**, and prefer describing structure to naming classes.
- **Run the script above** occasionally, and read its output rather than failing a build on it.
- **Or have it checked on every pull request.** This is what the MCP finding looks like when Striff posts it:

It reads the documents already in the repository, so there is no rule file to write and nothing to configure. It is free on public repositories.
